# 0004 — Android app: Compose shell over the existing Rust engine

- Status: accepted
- Date: 2026-11-05
- Applies to: v0.3

## Context

The desktop product is a single Rust binary with a CLI and a TUI. The phone needs a
real app: touch UI, background-tolerant networking, and the same cryptographic
identity, protocol and mailbox code — a second implementation of the crypto would
be a second source of bugs, and the protocol is not something to re-derive in
Kotlin.

Constraints:

1. No Android SDK, NDK or Google Maven access in the build sandbox: the app can only
   be compiled by CI.
2. The engine is blocking (`rusqlite` with bundled SQLite, `rustls`, synchronous
   sockets) and expects a filesystem it can write to.
3. Credentials are the most dangerous thing the project touches, and a phone is the
   device most likely to be lost.

## Decision

### One engine, one bridge, one string

`crates/android-jni` produces `libsocial_mail_android.so` and exports exactly one
function:

```text
Java_tld_android_social_Core_call(request: String) -> String
```

Every app action is a JSON command on that bridge (`status`, `feed`, `post`,
`sync`, `settings_set`, …). One string in, one document out (`{"ok": true, "data":
…}` or `{"ok": false, "error": "…"}`).

Why one function rather than a typed JNI surface:

- The signature cannot drift from the Kotlin side.
- Adding a feature is a new match arm, not a new `external fun` and a rebuild of the
  mangled symbol name.
- Every failure is an ordinary Rust `Result`, so the bridge can answer with an error
  string instead of throwing from native code.
- It is testable without a device: `handle()` is plain Rust, and its unit tests run
  in the normal `cargo test`.

Costs: no compile-time type checking across the boundary, and JSON parsing on every
call. Both are acceptable at this size; the Kotlin models default every field and
ignore unknown keys, so a Rust-side addition never crashes an older app.

### UI

Kotlin + Jetpack Compose, minSdk 26, targetSdk 34, `tld.android.social`. Compose
because it needs no XML layout files and renders Persian text with the platform's
own bidi and shaping. One activity, a sealed `Screen` type for navigation, no
navigation library — the app has fewer than ten destinations.

The engine runs on `Dispatchers.IO` behind a `Mutex`; the UI reads a single
immutable `UiState` snapshot.

### Identity and credentials on the phone

- The identity file lives in the app's private directory (`/data/data/…/files`),
  which other apps cannot read on a non-rooted device.
- `allowBackup=false` and explicit data-extraction rules exclude it from cloud
  backup and device transfer: a key that leaves the device is a key you no longer
  control.
- The mail app password is held **in memory for the session only**. It is not
  written to `SharedPreferences`, not to the database, not to a file. Restarting the
  app means re-entering it. This is a deliberate downgrade in convenience for an
  upgrade in safety; an OS-keyring (Android Keystore) version is tracked in
  `TODO.md`.
- The password travels to the engine in the request document and is placed in the
  process environment for the duration of the call, exactly as the desktop binary
  reads it. It is never logged and never returned.

### Build and signing

`cargo-ndk` builds the core for `arm64-v8a`, `armeabi-v7a` and `x86_64`; Gradle
packages those `.so` files from `app/src/main/jniLibs`, which is generated by CI and
git-ignored. No Gradle wrapper jar is committed: CI installs Gradle 8.9 through
`gradle/actions/setup-gradle`, so the repository keeps no opaque binaries.

Signing is conditional on four repository secrets (`ANDROID_KEYSTORE_BASE64`,
`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`). When they
exist the APK is signed and `apksigner verify --print-certs` proves it in the log.
When they do not, the artefact is named `…-android-unsigned.apk` and the release
notes say so. Nothing is presented as signed when it is not.

## Alternatives considered

| Option | Why not |
|---|---|
| Rewrite the protocol and storage in Kotlin | Two implementations of signature canonicalisation and X25519 sealing, guaranteed to drift. |
| Run the CLI inside Termux | Not an app: no notifications, no launcher icon, hostile to non-technical users. |
| Embed a web UI served by a local Rust binary | Android has no supported way to keep such a daemon alive, and it weakens the "private keys never leave the device" story. |
| `flutter_rust_bridge` / `uniffi` | Both are good; both add a code-generation step and toolchain that could not be exercised in this phase. The JSON bridge is ~600 lines and testable in plain `cargo test`. |
| AAB instead of APK | The deliverable is a sideloadable file for people who do not use the Play Store. An AAB is produced only when a store listing exists. |

## Consequences

- The phone and the desktop share every line of protocol, crypto, storage and
  transport code; a bug fixed once is fixed in both.
- The Android build depends on the NDK, `cargo-ndk` and Google Maven, so it is
  slower than the desktop build and can be rate-limited (mitigated with a Maven
  Central mirror and retries).
- The app cannot yet restore a desktop identity from a backup; that is the most
  important missing piece and is first in `TODO.md`.
- No background sync: the app syncs when it is opened or when the sync button is
  pressed.
